Part 1 — Foundations

Types of Prompting

Three foundational strategies, each giving the model a different amount of guidance. Choose based on task complexity and output predictability.

Zero-Shot
Few-Shot
Structured
Less guidance • Less predictable More guidance • More predictable

Zero-Shot Prompting

Give the model a task with no examples. Rely entirely on the model's pre-existing knowledge.

Classify the following movie review as POSITIVE, NEGATIVE, or NEUTRAL. Review: "The cinematography was breathtaking, but the plot felt rushed and predictable."

Best for: Simple tasks — summarization, classification, translation. Low ambiguity.

Few-Shot Prompting

Include 2–5 examples of input-output pairs before your actual query.

Extract the product name and price from each sentence. Sentence: "The new AirPods Max are available for $549." Product: AirPods Max Price: $549 Sentence: "You can get the Galaxy S24 Ultra starting at $1,299." Product: Galaxy S24 Ultra Price: $1,299 Sentence: "The Kindle Paperwhite is on sale for $129."

Best for: Pattern matching. You're activating patterns the model already knows by showing success.

Structured Prompting

Combine explicit instructions, formatting rules, examples, and constraints into a single organized prompt.

## Task Extract all company names, founding years, and HQ locations. If a field is missing, write "N/A". ## Output Format Return a JSON array. Each object: - "company" (string) - "founded" (integer or "N/A") - "headquarters" (string or "N/A") ## Example Input: "Apple was founded in 1976 in Cupertino." Output: [{"company":"Apple","founded":1976,"headquarters":"Cupertino"}]

Best for: Production systems, automated pipelines, output consistency.

Part 1 — Advanced

Advanced Prompting Techniques

Techniques that unlock reasoning, self-correction, and multi-step problem solving. Click any card to learn more.

Chain-of-Thought
"Think step by step"

Ask the model to show its reasoning step by step before arriving at an answer. Each step constrains the next, surfacing errors before they compound.

# Zero-Shot CoT — just add this phrase: "Let's think step by step." # The model breaks down the problem, # showing verifiable intermediate steps.
Self-Consistency
Multiple paths → majority vote

Run the same CoT prompt N times (with temperature > 0), extract answers, pick the majority. Error correction through redundancy.

Cost: N times more API calls. Best for: Math, logic — any task with a single correct answer.

Tree of Thoughts
Branching + backtracking

Generalizes CoT from a single chain to a branching tree. At each step, generate multiple candidates, evaluate which are promising, continue only viable branches.

Best for: Puzzles, code debugging, strategic planning where early choices constrain later options.

ReAct
Thought → Action → Observe

Combines reasoning with the ability to take actions (search, query, call APIs) and observe results before continuing. The pattern behind most modern AI agents.

Thought: "I need to find when Python was created" Action: Search("Python programming language year") Observe: "Python was first released in 1991..." Thought: "Now I have the answer."
RAG
Retrieve → Inject → Generate

Retrieve relevant documents first, paste them into the prompt as context. The model generates answers grounded in real sources. Reduces hallucination, works with private data.

RAG separates what the model knows from what information it has access to. The most important pattern for production LLM apps.

Part 1 — Structure

Prompt Structure & Frameworks

A well-structured prompt is not a single sentence — it is an organized document with distinct sections.

Role Who the model should act as — "You are a senior data analyst"
Context Background information the model needs to understand the situation
Task The specific action to perform — clear, unambiguous instruction
Constraint Rules, limits, and boundaries — what NOT to do
Format How the output should look — JSON, markdown, numbered list
Examples Input-output pairs showing the expected behavior

PRISM

PPersona— who the model acts as
RRequest— what you want done
IInformation— context and data
SStyle— tone and voice
MMode— output format

Best for quick internal tools and prototyping.

KERNEL

KKnowledge— domain-specific facts
EExpectation— acceptance criteria
RRole— expert identity
NNuance— edge cases, exceptions
EExamples— demonstrations
LLanguage— terminology, tone

Best for complex domains and regulated output.

Full PRISM Example

## Persona You are a senior backend engineer specializing in API security. ## Request Review the following REST API endpoint and identify security vulnerabilities. ## Information @app.route('/user/<user_id>', methods=['GET']) def get_user(user_id): query = f"SELECT * FROM users WHERE id = {user_id}" result = db.execute(query) return jsonify(result.fetchone()) ## Style Be direct and technical. Prioritize severity. ## Mode Numbered list: vulnerability name, severity, explanation, fix.

Architecture Patterns

Single Agent

User → [ Agent + Tools ] → Response
Best for most tasks. Start here.

Sequential Pipeline

User → Researcher → Writer → Editor → Out
Multi-stage workflows, different skills per stage.

Delegation

When one agent needs specialized sub-capabilities.

Debate / Parallel

Diverse perspectives, quality assurance, creative tasks.

ReAct: Theory vs. Practice

Theory (Text in Prompt)

Thought: "I need the time" Action: GetTime() Observation: "3:42 PM" Thought: "Now I can answer" # All text in the prompt # No real execution

Practice (Real Agent)

LLM decides to call get_time() Runtime executes the function Returns "3:42 PM" to LLM LLM generates final reply # Real code execution # Actual tool calls

Deep Dive

Under the Hood

The mechanics that explain why LLMs behave the way they do — and why certain techniques work.

The Great Asymmetry: Input vs. Output

LLMs can read a million tokens in parallel, but must write one token at a time. Input is processed all at once through matrix multiplication on GPUs. Output is autoregressive — each new token depends on every previous token, forcing sequential generation.

This is why you can paste an entire codebase into the prompt (fast), but the model's response is capped at 4K–32K tokens (slow, expensive). LLMs are speed-readers with a typewriter.

Input (Parallel)
128K – 2M tokens
Output (Sequential)
4K – 32K tokens
Why output is limited: Generating token N requires running attention over all N−1 previous tokens. Each token adds latency. A 100K-token output would take minutes and cost a fortune in compute. The input has no such constraint — it's one big parallel matrix operation.

Prefill vs. Decode

Inference has two distinct phases with very different performance characteristics:

Prefill
Process entire input prompt in parallel
GPU-parallel, fast
→
Decode
Generate tokens one at a time
Sequential, slow
The KV Cache stores computed attention values during prefill so they don't need recalculating for each output token. This is why "time to first token" is slow (prefill) but subsequent tokens stream faster (decode with cache). The KV cache is also why long contexts eat so much GPU memory.

Attention is O(n²)

Every token attends to every other token. Double the context length, quadruple the compute. This is the fundamental bottleneck of transformer architectures.

4K context → 16M attention ops
32K context → 1B attention ops
128K context → 16B attention ops
1M context → 1T attention ops
Innovations like Flash Attention (tiling for GPU memory), Ring Attention (distributing across devices), and sliding window attention make large contexts practical — but the fundamental O(n²) cost is why providers charge per token.

Tokenization is Weirder Than You Think

LLMs don't see characters or words — they see tokens. A token might be a word, part of a word, a space, or punctuation.

"straw
berry
"
= 3 tokens

This is why LLMs famously struggle to count letters in "strawberry" — the word is split across token boundaries. The model never sees individual characters as atomic units.

Prompt implication: Whitespace, formatting, and even capitalization can change token boundaries, which can change model behavior. Common words = 1 token. Rare words = multiple tokens. Code is especially token-expensive (syntax, indentation).

Temperature: Creativity vs. Accuracy

At each step, the model produces a probability distribution over all possible next tokens. Temperature controls how that distribution is sampled.

temp=0 — Always pick highest probability. Deterministic*, factual.
temp=0.7 — Moderate randomness. Good default for creative tasks.
temp=1.5 — High randomness. Creative but error-prone.
*Temperature 0 isn't truly deterministic — floating-point rounding on different hardware can break ties differently. Top-p (nucleus sampling) is often combined with temperature: only sample from tokens whose cumulative probability exceeds p, preventing very unlikely tokens from appearing.

Why Chain-of-Thought Actually Works

A transformer has a fixed number of layers (~80–120). Each layer is one step of "reasoning." For simple tasks, that's enough. For complex tasks, it's not.

When you ask the model to "think step by step," each output token gets fed back in as input. This effectively gives the model extra computation steps — it's using output tokens as working memory.

The insight: More output tokens = more serial computation = better answers on hard problems. This is why CoT helps with math but not with trivia — trivia only needs pattern matching (one forward pass), while math needs multi-step reasoning (many forward passes via output tokens).

System Prompts Aren't Magic

The "system prompt" is not a special enforcement mechanism. It's just text prepended to the conversation. The model treats it as strong guidance, but it's still just tokens in context.

This is why "jailbreaks" can work — a sufficiently clever user message can outweigh system instructions, because it's all just token prediction. Safety requires multiple layers: system prompts + output filtering + model training.

For agents: This means your tool descriptions, persona instructions, and guardrails are all competing for attention weight in the same context window. Keep system prompts concise and high-signal.

Tool Use Is Just Structured Output

When an agent "calls a tool," the LLM is generating JSON. It doesn't execute anything. The framework parses the JSON, runs the real function, and feeds the result back.

// What the LLM actually outputs: { "tool": "roll_dice", "args": { "sides": 20 } } // Framework intercepts, runs Python, // feeds result back as new context
The LLM picks which tool to call based on the tool's name and docstring in the prompt. A poorly-named tool with no docstring = an agent that never calls it. Tool descriptions are prompt engineering.

The Reversal Curse

If a model learns "A is B," it does not automatically know "B is A." Training on "Tom Cruise's mother is Mary Lee Pfeiffer" doesn't mean the model can answer "Who is Mary Lee Pfeiffer's son?"

This happens because transformers learn directional token sequences, not bidirectional knowledge graphs. The attention pattern A→B doesn't create B→A.

Prompt hack: If you need the model to reason about a relationship in reverse, explicitly restate it in both directions in your prompt or use CoT to let the model work through the connection step by step.

Mental Models for Agents

1

Agents are loops, not lines

A prompt is input → output. An agent is input → think → act → observe → think → act → ... → output. It keeps going until it decides it's done.

2

Tools are the agent's hands

Without tools, an LLM can only think. With tools, it can do. A tool is just a Python function the agent is allowed to call.

3

Start simple, add complexity only when needed

Don't build a multi-agent pipeline when a single agent with one tool would work. The debug surface of a 3-agent system is 3x that of a single agent.

4

The instructions are everything

Same model, same tools, different instructions = completely different behavior. The debate arena proves this — same LLM, wildly different outputs.

5

Structured output is your best friend

Free-form text for humans. Pydantic models for code. If output feeds another system — another agent, a frontend, a database — use structured output. Always.
